Back History
O projeto começou como um sistema de estoque para um mercadinho, com a ideia central de controlar produtos, fornecedores, funcionários, clientes, vendas, compras, despesas e estoque em uma aplicação única. A base escolhida foi um backend em Django/Django REST Framework, com banco SQLite, e um frontend em React com Vite.

No início, a estrutura principal do banco foi criada com os modelos essenciais: Produto, Estoque, Fornecedor, Funcionario, Cliente, Venda, ItemVenda, CompraFornecedor, ItemCompra e Despesa. A primeira versão já estabelecia a ideia de que venda e compra não seriam apenas registros simples, mas operações compostas por vários itens.

Depois veio uma fase importante de importação e organização dos dados. A planilha do mercadinho foi tratada com scripts auxiliares, como o corretor de planilha e o comando importar_planilha.py, para transformar os dados originais em informações compatíveis com os modelos do Django. Essa etapa foi essencial para popular o sistema com clientes, produtos, estoque, fornecedores, vendas, compras e despesas.

Com os dados estruturados, o projeto passou a evoluir para uma API REST. Foram criados endpoints para listar, cadastrar, editar e excluir as principais entidades do sistema. Além dos endpoints CRUD padrão, surgiram endpoints mais específicos, como registrar venda, registrar compra, pagar fiado, consultar lucro mensal, consultar vendas do dia e alertas de estoque mínimo.

Um marco importante foi a criação do fluxo de venda. A venda passou a ser registrada de forma atômica: cria a venda, cria os itens vendidos, calcula subtotais, baixa o estoque automaticamente e atualiza o cliente quando existe fiado. Isso transformou a venda em uma operação real de negócio, não só em um cadastro visual.

Depois, o fluxo de compra também foi refinado. A compra passou a funcionar com cabeçalho e itens, permitindo registrar vários produtos dentro de uma mesma compra. Também foi ajustado o preço usado na compra para considerar o preço de custo dos produtos, deixando o cálculo mais correto para controle financeiro.

Mais tarde veio uma correção importante: compras passaram a gerar despesas automaticamente. A lógica foi centralizada no backend, sincronizando uma despesa da categoria Compra de mercadorias sempre que uma compra é criada ou editada. Ao excluir uma compra, a despesa vinculada também é removida. Esse ponto conectou o módulo de compras com o módulo financeiro.

No frontend, a aplicação começou com páginas simples de listagem e cadastro, e depois foi ganhando uma interface mais completa. Foram criadas páginas para vendas, compras, produtos, clientes, fornecedores, funcionários, estoque, despesas e detalhes/edição de registros. O sistema também recebeu navegação, botões reutilizáveis, inputs padronizados, selects pesquisáveis e mensagens de erro/sucesso.

Outra fase importante foi a melhoria da usabilidade nas listas. As telas ganharam paginação, filtros, ordenação, seleção múltipla, exclusão em lote, destaque de item editado e busca. Também foi criado um componente de pesquisa para melhorar a navegação entre registros, especialmente nas páginas de vendas e compras.

O projeto também teve uma etapa de performance percebida no frontend. Foi criado um cache de requisições para evitar recarregar as mesmas listas toda hora. Depois, esse cache precisou ser ajustado para não mostrar dados antigos após ações como cadastrar venda, editar compra ou marcar compra como entregue.

Mais recentemente, foram feitos ajustes finos nos fluxos de cadastro. O cadastro de compra passou a salvar corretamente o nome da compra, que antes era enviado pelo frontend mas ignorado pelo backend. Nas páginas de cadastrar venda e cadastrar compra, foi adicionado o botão de remover produto antes de finalizar o cadastro, deixando o formulário mais prático.

Também houve uma etapa de organização do ambiente. O INICIAR.py foi criado para facilitar a vida de quem roda o projeto: instala dependências Python, verifica node_modules, sobe o backend Django, sobe o frontend Vite e abre o navegador automaticamente.

Em termos de Git, o projeto passou por algumas divergências entre o main local e o origin/main. Houve um momento em que a correção de compra gerando despesas estava localmente separada dos commits mais recentes do GitHub. Depois foi feito o merge para deixar o projeto local com o commit mais recente do remoto e mantendo a atualização de compras/despesas.

Hoje, o projeto está em uma fase bem mais madura: ele já tem backend com regras de negócio, frontend funcional, dados importados, fluxo de vendas com estoque, fluxo de compras com despesas, listagens completas e melhorias de usabilidade. Ainda existem pontos de limpeza, como arquivos __pycache__ rastreados pelo Git e algumas melhorias possíveis no cache, mas a espinha dorsal do sistema já está bem estabelecida.
